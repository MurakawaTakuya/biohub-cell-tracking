# 守るべき判断の記録

後のセッションでも守るべき判断を記録する。実験の結果は `runs/` と README の表に書く。

## D001: 公開 Notebook の系統を土台にする

- 日付: 2026-09-23
- 判断: 残り 6 日なので、自前のパイプラインは作らない。上位の公開 Notebook（pilkwang の重みと Harmonic Fusion の後処理）を fork し、その上に変更を加える。
- 理由: 公開 LB では 0.947 に 726 チーム、0.948 に 128 チームが並んでいた。自己ベストは 7 月の 0.902 だった。
- 影響: 出力が同じなら同点になり、提出が早い方が上位になる。後から同じものを出すと、同点グループの最下位に並ぶ。

## D002: 学習データでのローカル CV を、公開の重みの評価に使わない

- 日付: 2026-09-23
- 判断: 公開の検出器（seed314159 など）は学習データの 199 動画すべてで学習されている（discussion 742064）。学習データの hold-out で測った値は in-sample になるので、LB の予測に使わない。
- 影響: 学習済みの動画での評価を、未知のデータに対する性能の推定には使わない。ただし、実装の検証、候補の誤り分析、変更の副作用の確認には使える（2026-09-25 の外部レビューを受けて修正）。信頼できる CV が必要な場合は、評価する動画を学習から外して自分で学習し直す。

## D003: 検証込みの Notebook は、設定を固定してから提出する

- 日付: 2026-09-24
- 判断: validator や ppsweep で学習データに対してパイプラインを実行し直す Notebook は、提出する前に、その実行が選んだ `ppsweep_selected.json` の overrides を環境変数で固定し、`BIOHUB_VALIDATOR_ENABLE=0` にする（`server/make_fast.py`）。
- 理由: B002 は公開テストで 4.0 時間かかり、提出後の非公開テストでの再実行が 2 件とも時間切れで失敗した。
- 影響: 固定した版は、元の版と `submission.csv` が完全に一致することを確かめてから提出する（B004 と E002 で確認済み）。

## D004: 提出の失敗は `errorDescription` で確認する

- 日付: 2026-09-24
- 判断: 提出の status が COMPLETE でも、`publicScore` が空なら失敗として扱う。原因は API の `errorDescription` で確認する。
- 理由: B002 は COMPLETE と表示されていたが、実際には時間切れだった。

## D005: Kaggle の GPU quota と提出の関係

- 日付: 2026-09-24
- 事実:
  - 提出できるのは、Kaggle 上で保存のための実行（push 後の実行）が成功した Kernel バージョンだけ。この実行は GPU quota を使う。
  - 提出後の非公開テストでの再実行は、quota を使わないはず（未確認）。
  - バッチ GPU のセッションは、別コンペの分も含めて同時に 2 つまで。
- 判断: quota が切れても、実行済みのバージョンは提出できる。そのため、出す可能性のある案は quota が残っているうちに Kaggle で実行しておく。
- 研究室サーバーと Colab は、開発やテストには使える。ただし、提出するバージョンを作る実行の代わりにはならない。

## D006: 公式ルールで確認した事実（2026-09-25）

`kaggle competitions pages biohub-cell-tracking-during-development --content --page-name <Timeline|Code Requirements|rules>` で確認した。

- 最終提出の締切: **2026-09-29 23:59 UTC**（日本時間 9/30 8:59）。
- 提出は **1 日 5 回まで**。最終提出として選べるのは **2 本まで**。
- Notebook の実行時間の上限: **12 時間**（CPU、GPU とも）。インターネットは無効。公開されていて誰でも使える外部データや学習済みモデルは使ってよい。
  - B002 は公開テストで 4.0 時間かかり、非公開テストでの再実行が 12 時間を超えた。つまり、非公開テストでの再実行は、公開テストでの実行より 3 倍以上長くかかる。x138 系は公開テストで約 0.3〜0.4 時間。B005、E006、E010 は非公開テストでの再実行を実際に完了している（公開 LB が出た）。ただし、時間の余裕がどれだけあるかは確認できていない。x138 の 7.5 時間のガードは、動画の処理を始めるときにしか時間を見ない。また、ガードが効いた後も low-detection gapfill は続く（2026-09-26 の Codex レビューによる）。
- 規約の本文では、同点のときの扱いや、締切の時点でまだ採点中の提出の扱いは見つからなかった。Kaggle 全体の一般的な扱い（同点は提出が早い方が上位、最終提出を選ばなかった場合は公開 LB で上位の 2 本が自動で選ばれる）は、この規約では確認できていない。
- 判断: 最終提出は自分で選ぶ（自動で選ばれるのに任せない）。新しい提出は、採点に半日かかることを見込んで、遅くとも 9/28 のうちに出し終える。

## D007: 可視の test/ は学習データのコピーで、LB の採点対象ではない（2026-09-25）

- 公式のデータ説明（`--page-name data-description`）に、「test/ は学習データからコピーした例。提出して再実行すると、新しい非公開テストに差し替わる。非公開テストの大きさは学習データとほぼ同じ」と書いてある。外部レビューの 2 回目で指摘された。
- 影響:
  - 可視の 4 動画での件数（分裂 34 件、E007 との差 4 件など）は、その 4 動画での動作の確認であり、LB の差の原因を示すものではない。
  - 可視の 4 動画は学習データにもあるので、`.geff` の正解を使って診断できる。ただし、学習済みのデータでの診断であり、CV ではない。アノテーションは疎なので、正解にない細胞や分裂を、すべて誤検出として扱わない。
  - 非公開テストは可視の 4 動画の約 50 倍の大きさなので、可視テストでの実行時間から非公開テストの時間を見積もらない。x138 は、開始から 7.5 時間たつと修復の処理を簡略化する設定（`BIOHUB_REPAIR_DEADLINE_S=27000`）なので、非公開テストでは後半の動画で簡略化が起きている可能性がある（確認する手段はない）。

## D008: 最終提出は E013 + E010 のままにする（2026-09-27 夜、ユーザーの判断）

- 最終提出を 2 本目に E006（救う処理なし）へ替える案を検討した。非公開 LB では、2 本のうち高い方が最終の成績になるので、E010 は E013 とほぼ同じ失敗をかぶる。一方で、E006 に替えて得をするのは「救う処理そのものが非公開 LB で逆効果になる」場合だけで、守れる幅も救う処理で上がった分（公開 LB で +0.003〜0.004）が上限。
- シェイクの大部分は、土台の x138 と正解ラベルの誤り（discussion 742942）から来ると考えられ、2 本の選び方では防げない。
- 判断: ユーザーの方針（公開 LB の高い方を選ぶ）に従い、**E013 + E010 のまま**にする。
